# 2026-05-03 — v1 Phase 3: glue and polish

## Problem / Motivation

After Phase 1 (backend) and Phase 2 (dashboard), the repo had no
single-command bootstrap, no canonical `README` for newcomers, no
container manifests, and no `.gitignore`. Phase 3 closes those gaps so
the repo is handover-ready.

## Implementation Approach

**justfile as the source of truth.** Every operation lives there once.
The `Makefile` is a single line per target that calls `just`. The
PowerShell script is the only operationally distinct path because it
has to manage processes manually on machines without bash. Keeping the
recipes single-sourced means the README only documents one set of
targets and the others stay in sync by construction.

**`dev` runs redis + api + ui, not the agent.** This is deliberate. The
agent is a per-experiment thing: you pick episodes, seeds, speeds. Auto-
starting it during `just dev` would lock in defaults and waste the user's
attention. The README and the compose comment both say so explicitly.

**Compose binds to `127.0.0.1` only.** No exposed-to-LAN ports by
accident. Redis on 6379, API on 8000, UI on 5173, all loopback only.

**Compose excludes the agent and the duckdb.** The agent is a host
process that opens the DuckDB exclusively (DuckDB on Windows takes a
file lock), so containerising it would fight the native run. Mounting
the duckdb file into the API container would also be wrong because the
API doesn't read it; it only relays Redis. So the compose stack stays
narrow and the user runs `python -m agents.run_random` on the host.

**`Dockerfile` order optimised for layer cache.** `pyproject.toml` is
copied first; the `RUN pip install -e .` step caches as long as the
manifest doesn't change. Source copies happen before the install since
`setuptools.packages.find` needs the package directories on disk. (We
could split this further, but the install is fast and v1 doesn't need
it.)

## Mathematical / Statistical Details

No new numerics in this phase. The README documents the corrected
reward formula `r_t = log(equity_t / equity_{t-1}) - 0.05 * turnover_t`
that Phase 1 implemented. The 0.05 coefficient is approximately 10x the
0.001 taker fee, sized to discourage churn without crushing exploration
(see Phase 1 doc for the decomposition of the 1440-step random run).

## Design Decisions

- **just primary, make secondary.** just has cleaner positional args
  (`just agent 3 24 80 11`) and cross-platform shell semantics. make is
  retained as a one-line shim because some tooling and muscle memory
  expect `make test`. Single source of truth in `justfile` avoids drift.
- **No reverse proxy.** The API and the UI bind to different host ports
  (8000 and 5173). The dashboard reaches the API via
  `ws://127.0.0.1:8000/ws` from the user's browser, which works whether
  the API runs in docker, in `just api`, or in `scripts/dev.ps1`. A
  reverse proxy would let us put both on a single port but would also
  add a moving part for v1 to debug.
- **Vite dev mode in compose, not a production build.** v1 is a
  scaffold; HMR is more useful than a 200 KB minified bundle. v2 can
  add a `dashboard/Dockerfile.prod` with `npm run build` + a static
  server when there's a reason to deploy.
- **Portable Redis stays local-dev only.** The `.tools/redis/` zip is
  the dev-machine workaround we used because Docker, Memurai-via-winget,
  and WSL all failed. Phase 3's compose uses the official
  `redis:7-alpine` image, which is the canonical answer. The portable
  binary lives in `.gitignore`.
